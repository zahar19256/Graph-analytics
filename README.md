# Graph-analytics

## Краткое описание
В данном репозитории представлен вариант реализации алгоритма LeaderRank в стриминговом многопоточном формате. На вход принимается .csv файл, вида:
```
from,to
1,2 
2,3
3,1
4,1
Вместо from,to может быть пустой хедер или что-либо ещё не содержащее цифр.
```
## LeaderRank
**LeaderRank** — алгоритм оценивания вершин графа, с точки зрения их влияния. В отличие от PageRank, данный алгоритм не использует параметр затухания, вместо этого мы добавляем специальную вершину (*ground node*), соединённую со всеми вершинами графа, что обеспечивает устойчивую сходимость алгоритма и избавляет нас от трудностей с обработкой различных компонент связности графа.

Общий процесс вычисления алгоритма после добавления *ground node*, сводится к вычислению рангов следующей формулой:

$R_i^{(t+1)}=\sum_{j}\frac{R_j^{(t)}}{k_j^{out}},$ где:
- $R_i^{(t)}$ -- ранг вершины $i$ на итерации $t$
- $j$ -- вершина имещая ребро в $i$
- $k_j^{out}$ -- исходящая степень вершины $j$

После завершения итераций ранг дополнительной вершины делится между всеми вершинами графа, после чего полученные значения используются как итоговые оценки. Мой алгоритм оставливается при условии: максимальная разница на шаге оказалась меньше трешхолда $10^{-4}$
## Формат хранения данных:
Я хотел работать с графом чанками, так как имел опыт разработки колоночного движка. Поэтому я придумал следующий подход:
```
1) делим все ребра по бакетам
ребра попадают в один бакет, если у них совпадают from / FromBatchSize и to / ToBatchSize. Где FromBatchSize и ToBatchSize это выбранные мною константы.
2) за первый проход мы оцениваем сколько рёбер попадет в каждый из бакетов
3) далее мы записываем все бакеты в один файл формата `.graphZ` так чтобы у нас шли подряд бакеты с рёбрами у которых совпадает to/ToBatchSize. 
```
Такой формат хранения графа позволяет при подсчёте лидер ранга брать один бакет вершин, полностью проходиться обновлять их ответы. При этом from тоже посорчены в порядке возрастания номеров их батчей, что опять же позволяет читать с диска крупными блоками, сокращая общее число системных вызовов и лучше утилизирует возможности IO.

## Технические особенности:
Мой формат хранения данных на диске, предпологает, что вершины не помещаются в РАМ, поэтому было необходимо хранить вершины на диске, но для этого их необходимо предварительно уплотнить, чтобы не было свободных неиспользуемых вершин, которые создавали бы пустое пространство на диске и сильно бы нагружали IO. Для этого я реализовал k-мердж сорт. И алгоритм уплотнения вершин:

1) отсортить и убрать повторения среди всех вершин

2) считаем порядковые номера для всех вершин делаем mapping

3) дальше мы заменяем номера вершин в рёбрах на сжатые плотные версии для этого:

Делаем сорт вершин сначал по $from$ и замену номеров у $from$, потом сорт по $to$ и аналогично замена номеров по $to$.
Такой алгоритм уплотняет рёбра и решает проблему.
Следующего характера: при первом запуске своего алгоритма без внешнего сорта и
данной сжатия я получал файл с VertexInfo размером 12.4 ГБ на дата сете:
https://snap.stanford.edu/data/ego-Twitter.html 
Из-за чего каждая итерация алгоритма длилась от 70 до 100 секунд, так как было много переходов по почти пустому (заибтому нулями) файлу вершин.

Новый подход позволил сократить на этом же дата сете объём хранения вершин до мегабайт. И ускорил время работы до пары секунд. 

## Скорость работы:
На дата сете: https://snap.stanford.edu/data/soc-LiveJournal1.html 

Алгоритм отработал за 27 секунд конвертации + 0.4 секунды на одну итерацию алгоритма

Я брал специально крупный дата сет, чтобы отслеживать именно качество работы с IO. Ведь именно тут могут быть проблемы у стримингоового подхода.
## Как запустить

Собрать release-версию:

```bash
cmake -S . -B build-release -DCMAKE_BUILD_TYPE=Release
cmake --build build-release -j
```

Запустить алгоритм на CSV-файле:

```bash
./build-release/graph_analytics data/twitter_combined.csv out/twitter_combined
```

Результат будет записан в:

```bash
out/twitter_combined.leaderrank_reults.csv
```
